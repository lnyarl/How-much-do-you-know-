# Penumbra 코어 엔진 설계안

작성일: 2026-11-10

Penumbra의 현재 코어는 사용자가 무엇을 접했고 어떻게 이해한다고 표현했는지 기록한다. 사용자의 이해가 사실과 일치하는지는 판정하지 않는다. 직접 확인하지 않은 지식으로 관찰 범위를 확장하지 않는다. 향후 앎의 올바름을 관리하는 별도 엔진을 추가할 수 있으며, 현재 코어의 기록과 판정을 분리한다.

Go와 SQLite로 온톨로지, 대화 근거, 개인의 지식 표현을 관리한다. 외부 AI는 같은 코어의 조회와 피드백 계약을 사용한다. 이 문서는 코어의 구현 기준을 제안한다. 제품 코드는 포함하지 않는다.

## 1. 범위

첫 버전은 로컬 DB 하나에 한 사람의 지식 기록을 저장하는 Go 라이브러리다. 온톨로지 등록, 근거 저장, 관찰 제출, 개인의 진술 등록, 조회, 정정과 철회를 제공한다.

다음 기능은 코어 밖에 둔다.

- 소스에서 온톨로지를 추출하는 AI 작업
- 대화에서 관찰 후보를 추출하는 AI 작업
- 질문 생성, 학습 대화, 설명 생성
- 구독형 AI CLI 실행과 모델 API 호출
- MCP 서버, HTTP 서버, CLI 명령과 배포용 스킬
- 지식 지도 화면, 여러 기기 동기화, 다중 사용자 서비스
- 앎의 올바름을 검토하는 별도 엔진과 그 평가 데이터

이 기능들은 이후 코어의 계약에 연결한다. 첫 버전의 코어는 LLM 호출 없이 구조화된 입력과 저장된 근거만으로 실행할 수 있어야 한다.

## 2. 반드시 지킬 규칙

아래 규칙은 현재의 관찰 코어와 그 조회 및 피드백 계약에 적용한다. 향후 별도 엔진의 올바름 검토 결과도 이 코어의 관찰 사실로 혼입하지 않는다.

| ID | 규칙 |
| --- | --- |
| K1 | 정답, 오답, 오개념, 숙련도, 지식 점수를 산출하지 않는다. |
| K2 | 사용자가 표현한 내용이 소스와 달라도 그대로 기록한다. |
| K3 | 관련 개념, 상위 개념, 선수 지식을 안다고 추론하지 않는다. |
| K4 | 설명을 들었거나 질문에 응답했다는 사실을 이해로 바꾸지 않는다. |
| K5 | 응답 실패, 침묵, 검색 결과 없음은 모른다는 증거로 바꾸지 않는다. |
| K6 | 시간 경과만으로 망각이나 이해 저하를 생성하지 않는다. |
| K7 | 사용자에게 귀속하는 모든 관찰과 진술은 사용자 원문에 연결한다. |
| K8 | 자기보고, 실제 발언, 도움받은 활동, AI의 해석을 구분한다. |
| K9 | 정정과 철회는 기록으로 추가한다. 과거 기록을 조용히 덮어쓰지 않는다. |
| K10 | 외부 AI의 피드백도 정답 판정이나 근거 없는 사용자 상태를 기록할 수 없다. |

근거 구간이 존재한다는 구조적 검증만으로 AI의 해석이 정확해지는 것은 아니다. 코어는 원문과 구조를 검증한다. 의미 해석은 후보로 분리하고 사용자 지식의 확정 사실로 승격하지 않는다.

## 3. 온톨로지와 개인 지식 모델

### 3.1 공통 온톨로지

온톨로지는 개념의 식별자, 타입, 관계의 의미와 방향, 허용 연결을 정의한다. 사용자 이해의 올바름을 판단하는 기준으로 사용하지 않는다. 소스마다 서로 다른 설명과 관계가 있으면 출처를 구분해 보존한다.

초기 개념 타입은 `topic`, `concept`, `mechanism`, `procedure`, `example`을 제안한다. 타입은 표현 단위이며 사용자의 이해 수준이 아니다.

| 관계 타입 | 방향과 의미 |
| --- | --- |
| `is_a` | 구체 개념에서 분류 개념으로 연결 |
| `part_of` | 부분에서 전체로 연결 |
| `concretizes` | 구체 표현에서 추상 표현으로 연결 |
| `example_of` | 사례에서 대상 개념으로 연결 |
| `requires` | 어떤 소스가 선수 개념으로 연결한 방향 |
| `related_to` | 방향에 의미를 부여하지 않는 관련 관계 |

관계 타입별 허용 노드 타입을 레지스트리로 정의한다. 예를 들어 `example_of`의 출발 노드는 `example`이어야 한다. 위반 시 의미를 고쳐 저장하지 않고 입력 오류로 반환한다. 개념 타입을 추가하려면 버전이 있는 온톨로지 정의를 변경한다.

추상화는 `concretizes` 경로로 탐색한다. 모든 분야에 공통인 이해 레벨 숫자를 부여하지 않는다. 관계에는 소스 버전과 근거 구간을 붙인다. 소스에 없는 AI 생성 관계는 소스 관계로 등록하지 않는다. 추출기가 관리하는 후보와 등록된 관계를 구분한다.

동일한 이름의 개념을 자동 병합하지 않는다. 각 개념은 namespace와 안정적인 ID로 구분한다. 별칭 검색 결과도 병합 근거로 사용하지 않는다.

### 3.2 개인이 표현한 지식

개인 모델은 사용자의 발언, 자기보고, 직접 표현한 개념 간 연결을 보관한다.

```text
소스에서 정의한 관계
  Mutex → concretizes → 상호 배제

사용자가 표현한 내용
  "Mutex는 여러 스레드가 동시에 접근하지 못하게 하는 것이다."

조회 결과
  Mutex에 대한 사용자 설명과 원문을 제공한다.
  상호 배제나 스레드의 이해 여부는 미확인으로 남긴다.
```

사용자가 표현한 문장을 구조화할 때도 원문을 유지한다. 주어, 관계, 대상이 불명확하면 문장 그대로 저장하고 구조화된 진술은 만들지 않는다. 대명사나 생략된 개념을 임의로 보충하지 않는다.

명시적으로 표현한 연결은 개인의 진술로 저장할 수 있다. 예를 들어 "트랜잭션은 경쟁 상태를 모두 방지한다"는 발언을 그대로 보관한다. 이 진술을 공통 온톨로지의 관계로 자동 복사하지 않는다.

### 3.3 첫 버전의 표현 방식

SQLite에서 타입이 있는 노드와 관계, 출처가 있는 진술을 표현한다. 관계 타입과 제약이 정의된 온톨로지로 운영하되 첫 버전에 RDF 저장소나 OWL 추론기를 도입하지 않는다. 그래프 경로를 찾는 기능과 사용자 지식을 추론하는 기능은 구분한다.

대안인 범용 RDF와 OWL 중심 설계는 교환과 논리 추론이 필요한 경우 다시 검토한다. 현재는 관찰하지 않은 사용자 지식을 추론하지 않는 계약과 로컬 배포가 우선이다. 향후 RDF 내보내기는 저장 모델을 바꾸지 않고 추가할 수 있다.

## 4. 데이터 모델

ID는 외부에서 재사용할 수 있는 문자열이다. 시간은 UTC로 저장한다. `observed_at`은 원래 대화 시점이고 `recorded_at`은 Penumbra에 저장한 시점이다. 나중에 수신했다는 이유로 더 최근의 사용자 발언으로 취급하지 않는다.

| 엔티티 | 핵심 필드 | 역할 |
| --- | --- | --- |
| `store_meta` | profile_id, schema_version, ontology_version, data_revision | DB 소유 범위와 버전 |
| `sources` | id, namespace, title | 소스 식별 |
| `source_versions` | id, source_id, content, content_hash | 소스 원문과 변경 이력 |
| `concepts` | id, namespace, kind, label | 안정적인 개념 식별 |
| `concept_aliases` | concept_id, alias | 검색용 이름 |
| `concept_sources` | id, concept_id, source_version_id, quote_span | 개념과 소스 구간의 연결 |
| `relation_types` | id, allowed_subject_kinds, allowed_object_kinds, symmetric | 관계의 의미와 연결 제약 |
| `concept_relations` | id, subject_id, relation_type_id, object_id, source_version_id, quote_span | 소스에 근거한 관계 |
| `sessions` | id, producer_id, external_session_id | 피드백을 보낸 대화의 출처 |
| `messages` | id, session_id, external_message_id, role, content, observed_at | 변경하지 않는 대화 원문 |
| `observations` | id, kind, message_id, quote_span, assistance, context_message_ids, recorded_at | 원문에서 확인할 수 있는 사건 |
| `observation_concepts` | id, observation_id, concept_id, binding, confirmation_observation_id | 관찰과 직접 언급한 개념의 연결 |
| `personal_assertions` | id, observation_id, subject_id, predicate_text, object_text, object_concept_id, binding, confirmation_observation_id | 사용자가 표현한 내용과 관계 |
| `amendments` | id, target_type, target_id, action, replacement_id, reason, evidence_ref | 연결 정정과 기록 철회 |
| `receipts` | producer_id, request_id, payload_hash, result, revision | 재전송 처리 |

`quote_span`은 원문의 UTF-8 바이트 구간과 인용 문자열을 포함한다. 구간은 문자 경계와 일치해야 하고 인용 문자열은 실제 원문과 같아야 한다. DB 밖에 있는 파일 경로만으로 근거를 대신하지 않는다.

사용자 원문은 `role=user`인 메시지다. AI가 생성한 사용자 요약은 사용자 원문으로 등록할 수 없다. AI의 설명을 저장할 수는 있지만 사용자 지식의 증거로 연결하지 않는다.

`binding`은 `explicit`, `user_confirmed`, `candidate`로 구분한다. 문자열이 명시적으로 일치하는 모호하지 않은 이름 연결 또는 사용자가 개념을 지정한 연결만 기본 조회에 포함한다. `user_confirmed`에는 사용자 확인 발언인 `confirmation_observation_id`가 필수다. 확인 발언에는 대상의 모호하지 않은 이름 또는 namespace가 포함된 ID가 있어야 한다. 단순한 "네"만으로 대상을 연결하지 않는다. 후보 연결은 별도 조회에서만 보인다. 동음이의어 등으로 대상이 모호하면 후보로 남긴다.

직접 언급한 여러 개념을 하나의 관찰에 연결할 수 있다. 연결된 개념 전체를 안다는 의미는 아니다. `personal_assertions`는 하나의 발언에서 직접 표현한 내용만 담는다. 여러 발언을 합쳐 새로운 믿음이나 관계를 만들지 않는다. 구조화된 진술이 원문에 부합하는지는 자동으로 보장할 수 없으므로 AI 생성 진술은 후보로 표시하고, 기본 맥락에는 원문을 제공한다.

외래 키, 열거형, 필수 근거, 원문 구간, 중복 키는 저장 시 검증한다. 자기 참조를 허용하지 않는 관계는 거부한다. 첫 버전은 소스 그래프의 모든 순환이 잘못이라고 가정하지 않는다. 탐색 시 방문 집합과 깊이 제한을 사용한다.

## 5. 관찰 종류와 시간에 따른 변화

| kind | 기록하는 사건 | 기록하지 않는 결론 |
| --- | --- | --- |
| `user_explanation` | 사용자가 자신의 설명을 제시함 | 설명이 옳음, 관련 개념도 이해함 |
| `user_claims_familiarity` | 사용자가 안다고 말함 | 설명하거나 적용할 수 있음 |
| `user_claims_unfamiliarity` | 사용자가 모른다고 말함 | 인접 개념도 모름 |
| `user_reports_forgotten` | 사용자가 잊었다고 말함 | 과거 관찰이 무효임 |
| `user_reports_recalled` | 사용자가 기억났다고 말함 | 독립적으로 적용할 수 있음 |
| `user_requests_explanation` | 사용자가 설명을 요청함 | 해당 지식이 전혀 없음 |
| `user_confirms_reference` | 사용자가 발언의 대상 개념이나 연결을 확인함 | 그 개념에 관한 추가 이해 |
| `user_attempt` | 특정 질문이나 활동에 응답함 | 성공, 실패, 이해도 점수 |

`assistance`는 `none`, `hint`, `explanation`, `unknown`이다. 도움 여부가 확인되지 않으면 `unknown`으로 기록한다. 도움 없이 답했다고 추정하지 않는다. 질문과 힌트는 같은 세션의 메시지 참조로 연결한다.

망각과 회복은 원문에 있는 직접 보고로 제공한다. 오래된 발언에는 시간 정보를 붙인다. 자동 망각 상태나 점수 감쇠를 만들지 않는다.

```text
T1 사용자가 Mutex에 대한 설명을 제시함
T2 사용자가 "배웠는데 기억이 안 나요"라고 말함
T3 사용자가 설명을 요청함
T4 사용자가 "이제 기억났어요"라고 말함

결과: T1부터 T4까지의 사건을 시간과 출처와 함께 반환한다.
금지: T4 때문에 T2를 삭제하거나, 이해 수준이 상승했다고 판정한다.
```

T2의 대상 개념이 직접 확인된 경우에만 그 개념에 연결한다. 대상이 모호하면 후보로 남긴다. 외부 AI에는 `reported_forgotten`, `requested_explanation`, `reported_recalled`라는 관찰 신호를 전달한다. 신호는 발생 시점과 근거를 가진 사건이며 사용자의 현재 전체 상태를 뜻하지 않는다.

서로 다른 설명은 병렬로 보존한다. 코어는 모순 판정이나 진술의 우열 비교를 하지 않는다. 사용자가 이전 발언을 명시적으로 정정하면 정정 근거와 대상 ID를 연결한다. 최신 발언이라는 이유만으로 다른 설명을 자동 철회하지 않는다.

## 6. 코어 인터페이스

아래 이름은 Go 서비스 메서드의 제안이다. 전송 방식에 독립적인 요청과 응답을 사용한다. 모든 메서드는 `context.Context`를 받아 취소할 수 있어야 한다.

| 메서드 | 입력 | 출력 |
| --- | --- | --- |
| `RegisterOntology` | 개념, 별칭, 관계 타입, 관계, 소스 버전, request_id | 등록 ID와 revision |
| `SubmitFeedback` | 세션, 메시지, 관찰, 후보 진술, request_id | 저장 ID, 후보 여부, revision |
| `SearchConcepts` | 검색어, namespace, limit, cursor | 개념 후보와 다음 cursor |
| `GetContext` | concept_ids, max_items, max_bytes, include_candidates, cursor | 원문 기반 개인 맥락과 미확인 항목 |
| `GetEvidence` | observation_ids | 원문, 질문, 도움 조건, 정정 이력 |
| `ExploreOntology` | concept_id, relation_types, direction, depth, limit | 노드, 관계, 출처 |
| `GetConceptSources` | concept_id | 개념에 연결된 원문 구간과 소스 버전 ID |
| `GetSourceVersion` | source_version_id | 해당 버전의 원문 |
| `AmendRecord` | 대상, 정정 또는 철회, 이유와 근거, request_id | 수정 기록과 revision |

호출자는 단일 DB에 귀속된 profile만 다룬다. 외부 producer는 기록의 출처이며 인증된 사용자 신분을 뜻하지 않는다. 원격 인증과 권한은 향후 어댑터 책임이다. 코어를 원격으로 직접 노출하지 않는다.

### 6.1 조회 계약

`SearchConcepts`는 정확한 이름과 별칭을 먼저 찾고 부분 문자열로 후보를 추가한다. 첫 버전은 검색 순위를 지식 수준으로 해석하지 않는다. 한국어 형태소 검색, 임베딩, FTS는 필요가 확인되면 추가한다.

`GetContext`는 요청한 concept_ids의 직접 연결된 관찰만 반환한다. 관계 그래프를 따라 사용자 관찰 범위를 자동 확장하지 않는다. `ExploreOntology`의 관련 개념을 보고 호출자가 다음 조회를 결정한다.

응답은 다음을 구분한다.

- `observations`: 원문, 관찰 종류, 도움 조건, 시점, 근거 ID
- `candidate_bindings`: 별도 요청 시에만 제공하는 모호한 연결
- `unobserved_concept_ids`: 등록된 개념 중 유효한 직접 관찰이 없는 항목
- `unknown_concept_ids`: DB에 등록되지 않은 ID
- `signals`: 직접 보고된 망각, 회상, 설명 요청 사건
- `omitted_evidence`: 예산 안에 원문 전체를 담을 수 없는 관찰의 ID와 생략 이유
- `revision`, `truncated`, `next_cursor`: 조회 시점과 누락 여부

미확인 여부는 출력 예산으로 자르기 전 전체 유효 관찰에서 계산한다. 관찰이 있지만 출력에 생략된 경우 미확인으로 바꾸지 않는다. `signals`에도 근거 ID를 제공하며 정정 또는 철회된 관찰은 기본 결과에서 제외한다.

첫 버전은 LLM이 생성한 사용자 요약을 제공하지 않는다. 관찰은 메시지의 `observed_at` 내림차순과 관찰 ID 순으로 반환한다. 토큰 수는 모델마다 다르므로 코어는 항목 수와 UTF-8 바이트 예산을 사용한다. 원문을 문장 중간에서 잘라 새로운 의미를 만들지 않는다. 예산을 초과한 항목은 생략하고 페이지로 조회할 수 있게 한다. 단일 항목 자체가 예산보다 크면 ID와 생략 이유를 반환하고 cursor는 해당 항목 이후로 진행한다. 원문은 `GetEvidence`로 조회한다. 최소 응답 메타데이터조차 담을 수 없는 예산은 `INVALID_INPUT`이다.

페이지 cursor에는 revision을 포함한다. 저장 내용이 바뀌면 `STALE_CURSOR`를 반환해 첫 페이지부터 조회하게 한다. 한 응답은 하나의 SQLite 읽기 트랜잭션에서 생성한다.

  "external_session_id": "conversation-001",

판정 점수나 `knows_related_concepts` 같은 정의되지 않은 필드는 입력 단계에서 거부한다. 제출된 관찰 종류가 실제 발언과 맞는지에 관한 의미적 확실성은 응답에서 보증하지 않는다. 원문을 항상 함께 제공해 사용자가 정정할 수 있게 한다.

## 7. 저장과 오류 처리

기본 파일은 사용자가 지정한 로컬 경로의 SQLite DB다. WAL, 외래 키 검증, 유한한 busy timeout을 사용한다. 쓰기는 짧은 트랜잭션으로 처리한다. LLM 응답이나 네트워크 작업을 기다리며 트랜잭션을 유지하지 않는다.

하나의 제출 묶음은 메시지, 관찰, 진술, receipt, data_revision 갱신까지 원자적으로 저장한다. 하나라도 검증에 실패하면 전체를 저장하지 않는다. 저장 확정 전 종료되면 재시도할 수 있다.

`data_revision`은 실제 도메인 기록이 추가되거나 정정되는 트랜잭션마다 한 번 증가한다. 중복 요청과 내용이 같은 기존 기록의 재등록은 증가시키지 않는다. receipt만 저장하는 작업도 조회 revision을 바꾸지 않는다.

`producer_id + request_id`에 UNIQUE 제약을 둔다. 같은 키와 같은 정규화 입력이면 기존 결과를 반환한다. 같은 키의 내용이 다르면 `IDEMPOTENCY_CONFLICT`다. 정규화는 객체 키 순서를 고정하고 배열 순서는 보존한다. recorded_at처럼 서버가 생성하는 값은 입력 해시에 넣지 않는다.

원본 메시지는 `producer_id + external_session_id + external_message_id`로 중복을 막는다. 같은 외부 ID로 다른 원문을 제출하면 충돌이다. 관찰 ID도 재사용하며 같은 ID에 다른 내용을 넣을 수 없다. 다른 ID로 같은 원문이 재제출돼도 관찰 수를 이해의 강도로 사용하지 않는다. 의미가 비슷하다는 이유로 서로 다른 사용자 발언을 합치지 않는다.

정정은 원문을 수정하지 않고 잘못 연결한 개념이나 철회 대상을 지정한다. 대상 타입은 관찰, 관찰과 개념의 연결, 개인 진술, 소스 관계로 제한한다. `replace`는 미리 등록한 새 기록으로 기존 기록을 대체하며 `retract`는 기본 조회에서 제외한다. 사용자 발언의 의미를 정정하는 경우 사용자 정정 발언이 필요하다. 추출기의 연결 오류를 철회하는 경우 producer와 이유를 남긴다. 같은 DB 안의 존재하는 대상에만 적용하고 정정 연결의 순환을 금지한다. 철회된 관찰에 종속된 개인 진술과 신호도 기본 조회에서 제외한다. 기록 삭제와 개인 데이터의 완전 삭제 정책은 별도 기능으로 정한다. append-only 기록은 영구 보존 의무를 뜻하지 않는다.

| 오류 | 의미 |
| --- | --- |
| `INVALID_INPUT` | 알 수 없는 필드, 잘못된 타입 또는 예산 |
| `MISSING_EVIDENCE` | 필수 사용자 원문 또는 근거 없음 |
| `EVIDENCE_MISMATCH` | 인용 구간과 원문 불일치 |
| `UNKNOWN_REFERENCE` | 없는 개념, 메시지 또는 정정 대상 |
| `AMBIGUOUS_BINDING` | 모호한 연결을 explicit로 제출함 |
| `INVALID_RELATION` | 관계의 노드 타입 또는 연결 제약 위반 |
| `IDEMPOTENCY_CONFLICT` | 재사용한 키 또는 ID의 내용 불일치 |
| `STALE_CURSOR` | 조회 이후 데이터 변경 |
| `STORE_BUSY` | 제한 시간 내 DB 쓰기 잠금 획득 실패 |
| `SCHEMA_VERSION_UNSUPPORTED` | 지원하지 않는 DB 버전 |

`AMBIGUOUS_BINDING`은 동일 별칭 등 구조적으로 확인할 수 있는 모호성에 적용한다. 언어 의미의 모든 모호성을 탐지한다는 뜻은 아니다.

버전이 있는 순차 마이그레이션을 사용한다. 실패 시 해당 마이그레이션과 버전 변경을 함께 롤백한다. 지원하지 않는 최신 스키마에는 쓰지 않는다. 라이브 DB 백업은 SQLite backup API 계열을 사용한다. 실행 중인 DB의 본 파일만 복사하는 방식을 백업 계약으로 삼지 않는다.

                │
            engine.Engine
          ┌─────┼────────┐
       ontology  observations  context
          └─────┼────────┘

| 모듈 | 책임 |
| --- | --- |
| `engine/ontology.go` | 개념 식별, 관계 타입과 제약 |
| `engine/feedback.go`, `engine/amendment.go` | 원문 연결, 관찰 타입, 개인 진술, 정정 규칙 |
| `engine/query.go` | 직접 관찰, 미확인 항목, 제한된 그래프 탐색 |

첫 구현은 하나의 공개 Go 패키지 안에서 파일별로 책임을 나눈다. 별도 서비스로 배포하지 않는다. SQLite 드라이버는 `modernc.org/sqlite v1.60.1`을 사용하며 MCP 라이브러리는 아직 선택하지 않는다. 데이터베이스 포트를 범용 프레임워크로 확장하지 않고 실제 필요한 저장 연산만 정의한다.

### 8.1 향후 올바름 관리 엔진

올바름 관리 엔진은 사용자가 표현한 내용과 근거를 읽어 별도의 검토 결과를 만든다. 현재 코어에는 이 엔진의 실행, 평가 테이블, 판정 필드, 플러그인 구조를 구현하지 않는다.

확장 시 다음 경계를 유지한다.

- 검토 대상은 개념 전체에 대한 포괄적 이해도가 아니라 특정 개인 진술 또는 관찰 ID와 해당 내용이다.
- 검토 결과는 사용자 진술 및 관찰과 분리한다. 어떤 기준과 소스 버전으로 검토했는지, 검토 시점과 엔진 버전을 함께 남긴다.
- 검토 결과가 달라져도 원래 사용자가 표현한 내용과 관찰 범위를 덮어쓰지 않는다. 근거 없는 인접 지식 추론도 추가하지 않는다.
- 현재 `SubmitFeedback`에는 판정을 제출할 수 없다. 향후 별도 계약으로 전달하며 `GetContext`의 기본 관찰 결과와 구분한다.
- 교정 설명을 제공했다는 사실로 사용자의 지식이 바뀌었다고 기록하지 않는다. 이후 사용자 발언이나 자기보고를 새 관찰로 수집한다.

현재는 안정적인 관찰 및 진술 ID, 원문, 소스 버전, 정정 이력을 보존해 이 연결을 준비한다. 올바름의 기준, 검토 방식, 저장 구조는 해당 엔진을 설계할 때 정한다.

## 9. 외부 AI와 스킬의 계약

스킬은 코어의 사용 방법을 배포한다. 사용자 데이터는 스킬에 복제하지 않고 실행 시 조회한다.

1. 대화 주제를 검색해 개념 후보를 찾는다. 모호하면 대상 개념을 확인한다.
2. 해당 개념의 직접 관찰과 자기보고를 조회한다.
3. 사용자가 실제 사용한 표현을 설명의 출발점으로 삼는다. 그 표현을 세계에 관한 사실의 근거로 사용하지 않는다.
4. 미확인 영역을 배경 지식으로 가정하지 않는다. 필요한 경우 짧게 질문한다.
5. 새 발언을 원문과 함께 피드백한다. 관찰하지 않은 이해, 정답 여부, 설명의 효과를 추가하지 않는다.
6. 사용자의 망각 보고나 설명 요청에는 설명을 제공할 수 있다. 설명 제공 후 이해 또는 회복을 자동 기록하지 않는다.

코어가 규칙을 지켜도 외부 LLM이 지침을 따를지는 별도 통합 검증 대상이다. MCP 연결만으로 이 행동을 보장하지 않는다.

| 사례 | 필수 결과 |

| 시간만 경과 | 새로운 망각 사건이나 상태 변화 없음 |
| 잊었다고 직접 보고 | 시점과 근거가 있는 보고 신호 반환 |

| 모호한 개념 또는 생략된 대상 | 후보로 분리, 기본 사용자 맥락에 확정 연결 없음 |
| 관찰 없는 개념 | 미확인으로 반환, 모른다고 반환하지 않음 |

| 같은 제출 재전송 | ID, 결과, revision 유지 |
| 같은 키에 다른 제출 | 충돌 반환, 부분 저장 없음 |
| 원문 인용 불일치 | 전체 제출 거부 |
| 저장 도중 중단 | 전체 롤백 또는 확정된 동일 결과로 재시도 |
| 뒤늦게 과거 대화 수신 | 관찰 시점을 보존, 최신 보고로 덮어쓰기 없음 |
| 연결 정정 또는 철회 | 기본 조회에서 반영, 이력 조회에서 원래 근거 보존 |
| 페이지 조회 도중 새 기록 | 오래된 cursor 거부 |
| 재시작 후 조회 | 동일 revision의 맥락과 근거가 재현됨 |

| 4 | 보고 신호와 정정 | 망각 추론 없이 보고 보존, 철회 반영 |
| 5 | Go Engine 통합 | 위 검증 시나리오를 임시 SQLite DB에서 통과 |

핵심 엔진이 위 시나리오를 만족한 뒤 CLI, 스킬, MCP, 모델 실행기를 붙인다. 별도 인터페이스마다 사용자 지식 판단 로직을 다시 만들지 않는다.

### 11.1 구현과 검증 위치

Go 1.26 이상의 로컬 라이브러리로 구현한다. 저장 테이블은 JSON 본문과 조회 및 외래 키 검증을 위한 생성 열을 함께 사용한다. 소스 버전의 content_hash는 코어에서 SHA-256으로 계산한다. 온톨로지와 관찰은 같은 ID로 덮어쓰지 않는다.

- 공개 사용법과 실행 명령: [README](../README.md)
- 계약 및 SQLite 통합 테스트: [engine_test.go](../engine/engine_test.go)
- 실제 DB를 사용하는 호출 예제: [example_test.go](../engine/example_test.go)

AI가 구조화한 개인 진술은 기본적으로 후보다. 사용자 확인으로 등록하려면 확인 발언에 주어 개념과 진술의 관계 및 대상 텍스트가 직접 있어야 한다. 원문과 의미가 일치한다는 자동 보증은 제공하지 않는다.

현재 구현은 쓰기 중 오류의 전체 롤백과 재시작 후 데이터 및 receipt 보존을 검증한다. 프로세스를 강제 종료하는 장애 주입, 원격 AI 연동, 외부 LLM의 스킬 준수 여부는 별도 검증 범위다.

### 11.2 CLI와 스킬 연결

[cmd/penu](../cmd/penu/main.go)는 로컬 CLI 진입점이며 [internal/cli](../internal/cli/cli.go)가 인자를 코어 요청으로 변환한다. SQLite 스키마와 관찰 규칙은 CLI마다 다시 구현하지 않는다.

CLI는 JSON 성공 응답을 stdout으로, 구조화된 오류를 stderr로 반환한다. init만 저장소를 생성한다. JSON 파일과 stdin을 지원하고, 알 수 없는 필드와 중복 키를 코어의 엄격한 디코더로 거부한다.

[penumbra 스킬](../skills/penumbra/SKILL.md)이 기존 AI의 진단, 설명, 원문 수집, 피드백 행동을 정의한다. AI는 사용자 원문과 스킬의 요청 형식으로 피드백을 제출한다. 소스에 기반한 설명을 위해 개념의 출처와 원문을 읽는 조회 메서드를 추가한다.

스킬은 사용자 데이터와 별개로 배포한다. 이 저장소에서는 스킬 파일을 직접 읽도록 지정하고 ./bin/penu를 사용하면 된다. 개인 DB는 초기화 시 빈 상태이며 examples의 가상 발언은 별도 데모 DB에만 등록한다.
